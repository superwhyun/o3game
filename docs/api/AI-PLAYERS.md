# 외부 모델 AI 플레이어

관리 본부 → **User Management → AI 봇**에서 모델 API를 등록하고 AI 플레이어를 생성합니다. 모델 설정의 기본 모델 체크를 저장하면 이전 기본 모델이 해제되고 새 플레이어의 모델 선택에 자동 적용됩니다. API에서 modelId를 생략해도 활성 기본 모델을 사용합니다. 조회는 관리자, 설정 변경·생성·연결 테스트는 최고 관리자(superadmin) 권한이 필요합니다. 일반 사용자와 동일한 시작 자원·건설·연구·함대 규칙을 사용하며 자원 지급이나 관리자 명령을 사용하지 않습니다.

## 지원 제공자

| 제공자 | API 기본 주소 | 모델 ID / 인증 |
|---|---|---|
| OpenRouter | `https://openrouter.ai/api/v1` | 제공자의 모델 ID, API 키 필수 |
| Vercel AI Gateway | `https://ai-gateway.vercel.sh/v1` | Gateway 모델 ID, API 키 필수 |
| 로컬 / OpenAI 호환 | 관리자가 입력, 예: `http://host.docker.internal:11434/v1` | 서버의 모델 ID, 키는 선택 |

모두 비스트리밍 `POST /chat/completions`와 `choices[0].message.content`를 사용합니다. [OpenRouter 공식 API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request), [Vercel 공식 호환 API](https://vercel.com/docs/ai-gateway/openai-compat/rest-api) 기준입니다. 로컬 서버도 이 응답 형식과 messages/model/temperature/max_tokens를 지원해야 합니다. Docker의 localhost는 컨테이너 자체이므로 호스트 모델에는 host.docker.internal이나 접근 가능한 LAN 주소를 사용합니다. 로컬 모델은 Docker에서 접근 가능한 인터페이스에 바인딩해야 합니다. `/v1`까지 입력하며 `/chat/completions`는 서버가 붙입니다. 리다이렉트는 허용하지 않습니다.

키는 JWT_SECRET에서 도출한 AES-256-GCM 키로 암호화해 DB에 저장합니다. 관리자 조회·플레이어·실행 프로그램에는 키를 반환하지 않습니다. 같은 제공자를 수정할 때 키 필드를 생략하면 유지합니다. 제공자를 바꾸면 기존 제공자 키를 전달하지 않으며 새 키를 입력해야 합니다. JWT_SECRET을 변경하면 등록한 모델 키를 다시 입력해야 합니다. 키 자체를 삭제하려면 키 없는 compatible 모델로 변경하거나 사용하지 않는 모델을 삭제합니다.

## 실행

`server/.env`에 기존 JWT_SECRET과 별도로 AI_WORKER_SECRET(32자 이상)을 설정합니다. 생성 예:

```sh
openssl rand -hex 32
```

DB replica set 초기화를 완료한 다음 기존 실행 방식에 맞춰 올립니다.

```sh
docker compose --env-file server/.env up -d server ai-player
```

프로그램은 Node 22 이상이며 추가 npm 패키지가 없습니다. 단독 실행은 다음 환경 변수를 지정하고 `node ai-player/index.js`를 실행합니다.

- GAME_API_URL: 게임 서버 기본 주소, 기본 `http://server:3000`
- AI_WORKER_SECRET: 서버와 동일한 실행 프로그램 인증 키
- AI_WORKER_ID: 선택, 실행 프로그램 구분 이름(영문·숫자·하이픈·밑줄)

실행 프로그램은 HTTP API만 사용합니다. DB URI, 사용자 비밀번호, 관리자 토큰, 모델 제공자 키를 가지지 않습니다. 관리자에서 모델 등록 → 연결 테스트 → AI 플레이어 생성 순서로 진행합니다. 연결 테스트와 플레이어 실행에는 실제 모델 호출 비용이 발생할 수 있습니다. 모델 등록만으로는 호출하지 않습니다. 주기(15~3600초), 전략, 최대 보유 행성(1~9), 공격 허용 여부를 플레이어마다 조절할 수 있습니다. 새 플레이어의 공격은 기본 비허용입니다. AI 계정 삭제는 기존 User Management에서 하며 AI 설정도 함께 정리됩니다. 호출 제한이나 지출 예산은 제공자에서 설정하고 관리자에서 중지할 수 있습니다.

## 동작과 범위

1. 실행 프로그램이 `/api/ai-worker/claim`으로 실행할 플레이어 한 명을 받습니다. 120초 임대와 2분짜리 일반 게임 JWT가 발급됩니다. 동시 실행 프로그램의 중복 임대를 막습니다.
2. `/api/auth/me`, 카탈로그, 보유 행성 성계, 최근 정찰 성계 및 순환 탐색하는 원격 성계 API를 조회합니다. 자원·선행 조건·대기열·면적을 확인한 건설/연구/생산, 다른 보유 행성 선택, 정찰, 함대 생성/배치, 개척, 허용된 공격 후보와 대기 후보를 만듭니다.
3. `/api/ai-worker/decide`가 등록한 **외부 모델**을 호출해 후보 ID 하나를 선택합니다. 규칙으로 행동을 대신 선택하지 않습니다. 잘못된 모델 응답은 행동 없이 오류로 기록합니다. 이름과 설명은 명령으로 취급하지 않습니다.
4. 실행 직전에 사용자 상태를 다시 읽고 선택한 명령이 여전히 가능한지 확인합니다. 행성 선택, 자원, 작업 대기열, 연구·건물 레벨 또는 함대 상태가 달라져 후보가 사라지면 실행을 보류하고 다음 차례에 재판단합니다. 이후 게임 API 명령 하나만 호출합니다. 자원·선행 조건·함대 상태의 최종 검증은 게임 서버가 수행합니다. 함대/정찰은 UUID 요청 ID, 편성은 expectedRevision을 사용합니다.
5. `/complete`로 최근 행동·판단 이유·오류 코드·실행/행동 횟수를 저장합니다. 완료 후 설정 주기가 지나면 다음 판단을 합니다. 10초마다 별도 연결 상태를 알립니다.

플레이어 중지는 활성 임대를 무효화하고 후속 API 명령을 막습니다. 이미 서버에 반영된 건설이나 출항은 취소하지 않습니다. 모델 설정 비활성화는 다음 모델 호출을 막습니다. 실행 프로그램이 죽으면 임대 만료 후 재개합니다. 타임아웃에서 성공 여부가 불확실한 게임 명령은 자동 재시도하지 않고 다음 차례에 상태를 다시 읽습니다. 임대 만료 복구는 이미 실행된 명령을 되돌리거나 exactly-once 실행을 보장하지 않습니다.

현재 자동 플레이는 보유 행성의 성계 내 정찰·개척·공격을 지원합니다. 성계 밖 탐색, 수송·거래·철거·함대 회수는 자동 후보에 넣지 않습니다. 모델의 장기 전략 수준은 선택한 모델에 따라 달라집니다. 모델 제공자에게 자신의 게임 상태와 API로 관측 가능한 정보를 전달합니다.

## 오류

공통 `{error, code, requestId}` 및 `X-Request-Id` 계약을 따릅니다. 전체 경로·입출력은 [OpenAPI](openapi.json)에 있습니다.

| 코드 | HTTP | 의미 |
|---|---|---|
| AI_KEY_REQUIRED | 400 | 제공자 키 미입력 |
| AI_MODEL_DISABLED / AI_MODEL_IN_USE | 409 | 중지 모델 / 사용 중 모델 삭제 |
| AI_RUN_EXPIRED | 409 | 중지되거나 만료된 임대 |
| AI_PLAYER_INACTIVE | 403 | AI 게임 토큰의 실행 권한 소멸 |
| AI_WORKER_UNAUTHORIZED | 401 | 실행 프로그램 키 불일치 |
| AI_MODEL_RATE_LIMITED | 429 | 제공자 호출 제한 |
| AI_MODEL_AUTH_FAILED | 502 | 제공자 키 거부 |
| AI_MODEL_UNAVAILABLE | 502 | 제공자 접속/HTTP 실패 |
| AI_MODEL_INVALID_RESPONSE | 502 | 응답 JSON/텍스트/행동 ID 오류 또는 1MB 초과 |
| AI_MODEL_TIMEOUT | 504 | 제공자 응답 시간 초과 |
| AI_KEY_UNAVAILABLE | 503 | 암호화된 키 복호화 불가 |
| AI_WORKER_NOT_CONFIGURED | 503 | 실행 프로그램 인증 키 미설정 |

게임 API 오류는 그대로 최근 실행 오류에 기록합니다. API_TIMEOUT/API_UNAVAILABLE은 실행 프로그램이 게임 서버에 접속하지 못했을 때의 상태 코드입니다. 제공자 오류 본문과 API 키는 로그·HTTP 오류에 노출하지 않습니다. 모델 연결 제한 5~90초, 응답 토큰 128~4096, 판단 입력 750000자/512후보, 실행 프로그램 제어 API 600회/IP/분입니다. 제공자의 429는 다음 설정 주기에 다시 판단하며 제공자 Retry-After를 전달하지 않습니다.

현재 서버에는 `qwen3.8-27b`를 기본 모델로 등록했습니다. 게임 서버 컨테이너에서는 `http://host.docker.internal:1234/v1`로 호스트의 모델 API에 접근합니다. 이 등록은 현재 DB 설정이며 새 설치 환경의 모델 주소·실행 상태에 따라 관리자에서 등록해야 합니다.

## 플레이 중 개선 사항 제안

AI 플레이어의 **개선 사항 자동 제안**은 기본 활성화입니다. 같은 플레이 판단 호출에서 필요한 경우 `improvement:{title,description}`을 받으며 추가 모델 호출은 하지 않습니다. 판단에는 이전 행동/오류와 최근 공개 개선 요청 30건을 포함합니다. 게임/API에서 관측한 근거·영향·개선안을 작성하고, UI를 직접 봤다는 주장이나 근거 없는 오류, 자원 지급 요청은 제안하지 않도록 지시합니다. 유용한 제안이 없으면 null입니다. 모델의 추론 결과이므로 실제 반영 여부는 관리자 검토로 결정합니다.

실행 프로그램이 일반 게임 JWT로 `POST /api/game/improvement-requests`를 호출합니다. 목록에는 **AI 제안** 표시가 붙으며 기존 확인 완료·반영/부분 반영/거부 처리와 같습니다. `authorType`은 서버가 계정 종류로 정하며 클라이언트가 사칭할 수 없습니다. 제목 100자·내용 2000자 제한을 따릅니다. 제안 실패는 게임 행동과 별도로 기록하며 이미 성공한 게임 행동을 취소하지 않습니다.

- 봇마다 **6시간에 1건**만 등록합니다. 동시 등록도 같은 제한을 적용합니다.
- 최근 30일 내 동일한 AI 제목(대소문자·공백·문장부호를 정규화)은 봇이 달라도 차단합니다. 유사한 뜻의 다른 제목까지 서버가 판별하지는 않으며 최근 목록을 통해 모델에 반복을 피하도록 지시합니다.
- 관리자 User Management의 AI 봇에서 봇마다 자동 제안을 끌 수 있습니다. 기존 봇도 기본 활성화입니다.
- 관리자 카드에는 등록 제안 수와 최근 제안 오류가 표시됩니다.
- 오류: `AI_SUGGESTIONS_DISABLED` 403, `AI_SUGGESTION_DUPLICATE` 409, `AI_SUGGESTION_COOLDOWN` 429. 마지막 오류는 Retry-After(초) 및 details.nextAllowedAt/retryAfterSeconds를 제공합니다.

## 사용자 대리

사용자 설정에서 관리자가 등록한 활성 모델, 전략, 판단 간격, 개척 목표 및 공격 허용 여부를 선택합니다. 사용자 대리와 AI 봇은 기존 워커 프로세스를 공유하며 현재 한 작업씩 순차 처리합니다. 사용자마다 프로세스를 생성하지 않으며 모델 응답이 느리거나 계정이 많으면 판단 간격보다 실행이 늦어질 수 있습니다.

사용자는 대리 중에도 수동 명령을 내릴 수 있습니다. 실행 전 최신 상태 확인과 서버의 최종 검증을 함께 적용합니다. 사용자 대리는 계정 설정, 관리자 권한 및 행성 포기를 실행할 수 없습니다. 대리 중지는 임대를 무효화하고 이후 명령을 막으며 이미 승인된 작업은 계속 진행합니다. 비밀번호 변경도 대리를 중지하고 기존 로그인 토큰과 소켓을 무효화합니다.

관리본부에서 AI 플레이어를 생성할 때 배치 은하(1~9) 또는 자동 배치를 선택할 수 있습니다. `POST /api/admin/ai-players`의 선택 필드 `galaxy`는 정수입니다. 지정하면 해당 은하 안에서 빈 성계·궤도를 자동 선택합니다. 지정한 은하가 가득 차면 다른 은하로 넘어가지 않고 `409 RESOURCE_CONFLICT`를 반환합니다. 기존 플레이어 설정 변경은 첫 행성을 이동하지 않습니다.


## 무작위 배치와 행동 성향

User Management의 일반 사용자 / AI 봇 그룹에서 계정을 구분합니다. AI 봇 그룹에서 추가할 수(1~50), 이름 접두어, 모델과 성향을 입력합니다. 전체 은하를 선택하면 은하 1~9의 빈 좌표에서 무작위 배치하며 특정 은하로 제한할 수도 있습니다. 일괄 생성은 하나의 트랜잭션으로 수행합니다. 기존 봇 위치는 변경하지 않습니다.

`POST /api/admin/ai-players`에 `count`를 지정하면 `{players,created}`를 반환합니다(1개이면 `player`도 포함). 생략하면 기존 `{player}` 응답을 유지합니다. `behaviorScores:{development,expansion,attack}`는 각각 0~100 정수이고 합계가 100이어야 합니다. 봇별 PATCH로 수정할 수 있으며 시작·중지, 모델, 최대 행성 수, 개선 제안도 제어합니다. 점수는 모델의 행동 우선순위이며 행동 횟수의 고정 배분은 아닙니다. 공격은 공격 점수가 양수이면서 공격 허용을 켠 경우에만 후보로 등장합니다.

현재 성계에 빈 행성이 없어도 실행 회차에 따라 다른 성계와 은하를 탐색합니다. 정찰로 확인한 빈 행성에는 미편성 식민선을 직접 보낼 수 있습니다. 개발·정찰·개척은 자원, 면적, 함선 및 개척 한도 등 게임 조건을 충족할 때 진행하며 유용한 작업이 없으면 대기 후 최신 상태를 확인합니다.


봇의 중력자 연구는 실제 데스스타 선행 조건을 갖추고 공격이 허용된 경우 필요한 레벨까지만 후보로 제공합니다. 불필요한 중력자 연구가 이미 예약되어 있으면 가장 뒤쪽 레벨부터 기존 `DELETE /api/queue/{id}`로 취소하여 개척 연구의 병목을 해소합니다. 이 자동 취소는 AI 봇에만 적용하며 일반 사용자의 대리에게는 허용하지 않습니다. 대기열의 pending과 building 상태를 구분해 판단합니다.

작업 취소 시 같은 대기열의 뒤쪽 시작·완료 시간을 다시 연결합니다. 취소된 작업의 원래 완료 시각까지 기다리지 않으며, 이미 진행한 작업의 경과 시간과 예약된 소요 시간은 유지합니다. 이전 취소로 남은 미래 시작 시각의 공백도 상태 갱신 시 복구합니다.


AI 확장 판단에는 `expansionPlan`으로 보유 행성 수, 프로필의 개척 목표 상한, 전체 행성의 보유 식민선, 건조 대기열과 이동 중 식민선 수, 추가 생산 필요 수를 전달합니다. 상한에 도달하거나 기존 식민선이 남은 수요를 충족하면 식민선 생산 후보를 제외하고 실행 직전에도 최신 상태로 다시 확인합니다. 확장 성향 점수가 높아도 상한을 넘지 않습니다. 이 규칙은 AI 판단·실행에만 적용하며 일반 사용자의 수동 생산 규칙은 변경하지 않습니다.
