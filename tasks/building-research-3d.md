# 건설·연구 3D 전시와 건물 성장 외형

## 상태·요청·완료 기준

- 상태: 전체 구현·검증 완료, 최종 커밋 준비. 사용자가 구현과 완료 후 커밋을 명시적으로 요청했다.
- 기준: 2026-10-05 최신 harness/SKILL.md 및 framework/docs/HARNESS.md를 다시 읽었다. scaffold_task.py를 실제 실행해 이 문서 틀과 6개 실행 단위를 생성한 뒤 대상 코드 근거에 맞춰 내용을 작성했다. phase/step별 별도 파일과 별도 모델 CLI는 사용하지 않는다.
- 목표: 건설·연구 화면도 조병창처럼 목록에 모델 썸네일, 상세에 회전 가능한 3D 전시를 제공한다. 건물은 종류와 성장 구간이 외형으로 읽히고, 연구는 해당 기술의 실험 대상·장치를 알아볼 수 있게 한다.
- 전체 완료 조건: 현재 건물 12종·연구 15종에 고유한 시각 표현이 있다. 건물 4구간이 실루엣·설비 구조로 구별되고 실제 완료 레벨에 따라 갱신된다. 기존 건설·연구·조병창과 함대·정찰 경로를 유지하며 데스크톱/390px 모바일에서 조작·성능·실제 화면을 검증한다.
- 커밋: 구현 요청이 오면 단위별 검증을 통과한 동작 가능한 변경과 기록을 함께 커밋한다. 공통 뷰어 변경은 조병창 회귀까지 통과해야 커밋한다. push·원격 배포는 별도 요청 범위다. 이번 계획만으로 구현을 시작하지 않는다.

## 현재 코드 근거

- EntityBrowser는 건설·연구·조병창의 목록/상세 공통 UI다. UIManager.getBrowser에서 showModel은 조병창에만 켜져 있고, EntityBrowser.updateModel/renderList는 ship에 한정돼 있다.
- ShipViewer는 Three.js + OrbitControls, 조명·환경·카메라 자동 맞춤, 보일 때만 애니메이션을 사용한다. ShipThumbnails는 공용 오프스크린 렌더러와 직렬 작업 큐로 썸네일을 만든다. 기존 모델 팩토리는 userData.radius/update와 geometry 해제를 제공한다.
- server/data/catalog/buildings.js 12종, research.js 15종이 항목 정의의 단일 출처다. model은 specToDefinition → display.model → DB → 클라이언트 catalog.model 및 역직렬화 경로가 이미 있다. 현재 설명은 ship/defense 전용이며 시각 설정 검증은 확장해야 한다.
- EntityConfigService는 기존 DB display override와 seed를 합친다. 기존 DB에 새 model이 없어도 seed 시각 정보가 반영되는지 확인하고 관리자 변경/파일 동기화 왕복에서도 보존한다. 사용자 데이터 초기화로 적용하지 않는다.
- GameState.buildings/research의 실제 완료 레벨, EntityBrowser.amountOf 및 기존 큐 상태를 재사용한다. renderSpecs는 연구 효과가 없는 항목에 수치를 만들지 않는다.
- 시작 Git 상태: 게임 코드 tracked 변경 없음. 기존 .serena/와 artifacts/는 이 작업 범위 밖이다.

## 화면과 성장 규칙

### 건설

- 목록: 이모지 위치에 현재 성장 구간의 3D 정지 썸네일. 이름·실제 Lv·가능/진행 상태 유지.
- 상세: 지면 받침 위 시설 전경, 드래그 회전/확대/시점 초기화, 현재 Lv와 외형 구간 표시. 아래에 기능 설명·다음 레벨 효과·요구조건·비용·건설 버튼을 둔다.
- 구간 경계는 겹치지 않게 1~9 / 10~19 / 20~29 / 30 이상으로 정한다. 따라서 Lv 10·20·30에 외형 변화가 생긴다. 구간 내 개별 레벨마다 모델을 만들지 않는다.
- Lv 0: 1단계 시설의 설계 미리보기 + 명확한 미건설 표시. 이미 가동 중인 시설처럼 보이지 않게 가동 조명/장치 움직임을 끈다. 카탈로그 잠금 상태와 미건설 상태를 구별한다.
- 성장: 단순 크기/색 변화가 아니라 설비 수·보조 구조·동선·상부 실루엣·에너지 장치가 발달한다. 고레벨도 기본 시설 정체성을 유지한다. 30 이후에는 마지막 외형을 유지하고 실제 숫자 레벨만 증가한다. 외형 변경은 게임 성능 보너스를 추가하지 않는다.
- 상세에 현재 외형 / 다음 외형 구간 미리보기를 제공한다. 다음 구간 시작 레벨과 남은 레벨을 표시한다. Lv 9→10처럼 실제 다음 업그레이드가 경계를 넘으면 외형 변화 예정도 강조한다. 미리보기는 디자인 전시로 표시하며 실제 레벨·비용·건설 명령을 바꾸지 않는다. 마지막 구간에는 다음 미리보기를 비활성화한다.
- 공사 중에도 실제 완료 외형을 유지하고 큐 진행 상태만 표시한다. 완료된 서버 스냅샷에서 모델·썸네일을 함께 전환한다. 취소/실패/구버전 응답은 외형을 앞당기지 않는다.

### 연구

- 목록과 상세에 연구별 실험 장치를 표시한다. 모든 기술을 같은 연구소 건물이나 색깔만 다른 구체로 대체하지 않는다.
- 연구소는 건설의 researchLab에서, 기술의 실험 대상은 연구 화면에서 보여준다. 연구별로 짧은 '무엇을 연구하는가' 설명과 핵심 구성요소 2~3개를 모델 가까이에 둔다.
- 연구 단계 수치와 미연구/연구 중/완료 상태는 실제 데이터로 표시한다. 연구 외형은 우선 15종의 고유 장치 1종씩이며 건물처럼 4단계 성장 모델을 만들지 않는다. 연구 진행 시 장치 동작/스캔의 은은한 변화만 사용한다. 완료 레벨에 따른 기술 외형 확장은 후속 범위다.
- 장치 묘사는 시각 설명이다. 카탈로그에 없는 생산/피해/속도 효과나 실제 게임에 없는 연구 조건을 설명으로 약속하지 않는다. 현재 효과/해금은 기존 데이터와 실제 계산을 기준으로 표시한다.

### 사용성과 시각 방향

- 현재 게임의 어두운 우주 배경·금색 포인트를 유지하며 건물은 산업시설 디오라마, 연구는 실험실 전시로 구별한다. 모델 옆 설명은 짧게, 비용·명령 버튼은 명확하게 배치한다.
- 데스크톱은 목록 + 모델/상세, 모바일은 선택 목록 + 높이 제한 모델 + 명령 영역 순서다. 3D 확대 때문에 건설/연구 버튼이 계속 밀리거나 가려지지 않게 한다. 버튼 터치 영역 44px 이상, 가로 overflow 0.
- 회전은 드래그와 접근 가능한 회전/확대/초기화 버튼을 지원한다. 모바일은 한 손가락 페이지 스크롤을 우선하고 명시적인 모델 조작 상태에서 회전한다. 조작 해제로 스크롤을 복구한다.
- 자동 회전은 끌 수 있고 prefers-reduced-motion에서는 기본 정지 및 장치 효과 억제. 정보 전달을 애니메이션이나 색에만 의존하지 않는다.
- 모델 아래 연구 설명과 이름/레벨은 DOM 텍스트로 제공한다. WebGL 불가/컨텍스트 손실/모델 오류 시 정지 이미지 또는 기존 아이콘과 설명으로 복구하며 건설·연구 명령은 계속 사용할 수 있게 한다.

## 기술 계약과 변경 경계

- 기존 Three.js 절차적 모델 제작을 확장한다. 새 3D 엔진·외부 유료 모델·이미지 생성은 기본 범위에 없다. 공유 부품은 사용하되 항목별 실루엣/설비/재료 차이를 만든다.
- catalog model 제안: building `{kind: 'building', archetype, styleVersion: 1}` / research `{kind: 'research', archetype, styleVersion: 1}`. 성장 단계는 클라이언트의 공통 규칙으로 실제 레벨에서 계산한다. 기존 ship의 hull/faction 계약을 유지하며 타입별 분기한다. 스펙에 실행 함수/원격 URL은 넣지 않는다.
- 공통 ModelFactory/ModelViewer/ModelThumbnails 경계로 확장하고 ShipViewer/ShipThumbnails 외부 사용처는 호환 wrapper 또는 제한된 호출부 변경으로 유지한다. 함대 카드의 함선 썸네일도 회귀 범위다.
- 모델 반환 계약: root group + 중심/크기 + update(time) + 자원 정리. 건물은 지면/카메라 구도를, 연구는 받침/실험 구도를 제공한다. 카메라 맞춤은 외형 단계가 달라도 전체 설비가 잘리지 않게 bounds로 계산한다.
- 변화 키: type/id/model spec(styleVersion 포함)/성장 단계/미건설 상태. 같은 구간의 1레벨 상승이나 자원 tick마다 geometry를 재생성하지 않는다. 실제 구간 변화만 모델을 교체한다. 미리보기 키를 실제 상태와 구분한다.
- 비동기 썸네일은 타입·항목·구간을 포함해 캐시하고 오래된 요청 결과가 다른 항목/레벨에 적용되지 않게 요청 세대를 확인한다. 현재/가시 목록 먼저, 나머지 idle 생성. 실패한 캐시 promise를 영구 보관하지 않고 재시도 경로를 둔다.
- 공용 상세 렌더러 1개 + 공용 썸네일 렌더러 1개를 재사용하고 기존 우주 장면은 유지한다. 화면 전환/탭 숨김/뷰 제거 시 RAF·observer·controls를 정리한다. 환경 텍스처와 재질의 공유 소유권도 정해 중복 dispose/누수를 방지한다.
- 제안 성능 상한: 상세 모델 50,000 triangles/120 draw calls, 썸네일 캐시 최대 96개/48MiB 중 먼저 도달하는 제한. 실제 브라우저 baseline 측정 후 조정 근거를 기록한다. 반복 부품은 instancing/공유 geometry, 모바일 DPR 최대 1.5, 과도한 그림자·후처리는 사용하지 않는다.
- 27종 전체와 건물 4구간(48개) 및 연구 15개, 총 63개 핵심 외형을 모델 검토용 contact sheet/모델 전시 도구로 확인한다. Lv 0 상태와 잠금/진행 중은 별도 UI 검사한다. 대표 모델 3개(광산·로봇 공장·보호막)로 먼저 품질·성능 기준을 확인한 뒤 전체를 제작한다.
- 항목 누락/알 수 없는 archetype은 타입별 fallback으로 복구한다. 카탈로그 추가가 UI를 깨뜨리지 않게 한다. 모든 현재 항목의 매핑 누락은 테스트 실패다.
- server: catalog buildings/research, schema의 시각 설정 검증·직렬화 및 seed/DB merge 확인. 게임 비용·효과·큐·사용자 스키마는 변경 대상이 아니다.
- client: three 공용 전시·buildings/research 팩토리, EntityBrowser, UIManager, views.css/관련 스타일, 개발용 모델 검토 화면. 기술 트리 자체의 3D 배치와 행성 전체 도시 건설 장면은 범위 밖이다.

## 검증·실패·재개

- 자동 검사는 매핑/경계/캐시/상태/명령 회귀를 확인한다. 렌더러나 canvas가 존재한다는 사실만으로 시각 품질을 통과 처리하지 않는다. 전체 contact sheet와 대표 상세/모바일 화면을 직접 보고 형태·성장·가림·동작을 확인한다.
- 성능은 같은 장면의 10초 측정으로 p95 프레임 시간과 draw calls/triangles를 기록한다. 50회 항목/화면 전환 뒤 renderer context 수가 증가하지 않고 geometry·texture 수가 warm-up 수준으로 돌아오는지 검사한다. 저성능/실기기 미검증은 별도로 기록한다.
- 큐 완료 경계 테스트와 seed/DB 왕복은 별도 _test DB에서 실행한다. 실제 계정 레벨/자원/임무를 변경해 검사하지 않는다. 실제 화면에서 부족한 레벨별 외형은 개발용 전시/미리보기로 확인한다.
- 모델 로딩 실패·context 손실·미지원 스펙·낡은 비동기 응답은 해당 시각 영역 안에서 복구한다. 기존 건설/연구 요청과 소켓 스냅샷 적용 경로를 분리해 시각 오류가 게임 명령을 막지 않게 한다.
- 구현/검증/커밋 실패 시 해당 단위는 in_progress로 유지하고 원인·다음 행동을 이 문서에 남긴다. 시각 품질이 부족하면 색/크기만 바꾼 임시 모델로 완료하지 않고 해당 모델 단위에서 보완한다.
- 계획 작성 시에는 코드 구조와 항목 수를 확인했고, 이후 사용자의 명시적 구현 요청에 따라 아래 구현 결과까지 수행했다.
- 다음 행동: 검증한 이 기능의 변경과 기록을 커밋하고 최종 Git 상태를 확인한다. push는 하지 않는다.
