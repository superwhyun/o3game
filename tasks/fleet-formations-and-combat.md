# 함대 편성 저장과 전투 화면 분리

## 목표와 범위

- 상태: 5개 phase·20개 step의 로컬 구현 및 격리 검증 완료(2026-10-04). 기존 standalone 실행 DB의 기본 동작 복구 확인. 기존 Docker DB의 replica set 전환 및 실제 함대 생성·저장 API 확인 완료(2026-10-05). 원격 배포는 미실행. 스킬 변경은 요청대로 보류했다.
- 군사 메뉴는 `조병창 / 함대 / 전투`로 구성한다. 기존 함대 작전 화면은 전투로 옮기고, 새 함대 화면은 저장되는 함대 편성을 담당한다.
- 플레이 흐름: 함대 생성 → 함선 배정·저장 → 전투에서 함대 카드 드래그 → 목표·함대·ETA 확인 → 출격 성공 → 카드 제거 및 하단 진행 중인 임무 표시 → 귀환 완료 → 생존 함선으로 같은 함대 재사용.
- 서버에 편성을 저장하며 새로고침·재접속·다른 탭에서도 같은 결과를 보여준다.
- UI 개선도 필수 범위다. 사용자의 추가 요구인 "지금은 그냥 서류 같다"를 반영해 함선 이미지·편성 카드·지도와 동작 피드백을 중심으로 게임 화면을 재구성한다. 대상은 이번 함대·전투 화면과 군사 메뉴이며 다른 화면 전체 개편으로 확대하지 않는다.
- 사용자의 후속 구현 요청으로 작업을 실행했다. 기존 미커밋 작업 위에 필요한 변경을 적용했으며 별도 커밋/배포는 하지 않았다.
- 범위 밖: 새 전투 공식, 함대 간 합동 공격, 자동 보충, 새 정찰·식민 임무, 이동 함대의 지도 애니메이션.

## 설계 시작 시 코드에서 확인한 사실

- `ogame-3d/index.html`: 군사 `data-view="fleet"` 버튼과 `fleet-panel`에 지도·수동 명령서·작전 현황이 들어 있다.
- `UIManager.renderFleet/renderStrikeMap`: 보유 함선을 직접 고르는 임시 공격대와 좌표 입력 폼을 제공한다. 성계도의 목표 지정도 이 화면을 연다.
- `views/SquadComposer.js`: 수량은 컴포넌트의 Map에만 저장된다. `StrikeMap`은 단일 공격대 토큰에 드래그 이벤트를 붙인다.
- `User`의 `planets[].fleet`: 행성에 주둔 중인 함선 종류별 수량이다. 저장된 이름 있는 함대 모델은 없다.
- `POST /api/game/fleets`: 클라이언트가 보낸 수량으로 출격하며, 이동 문서 생성과 사용자 함선 차감을 별도 저장한다.
- `FleetMovement`: 임무·함선·좌표·시간·상태를 갖지만 편성 ID/함대 이름은 없다. 함선 필드도 카탈로그와 달리 고정 목록이다.
- `socket/handlers.js`: 5초 주기로 도착·전투·귀환을 처리한다. 귀환 시 함선을 원래 행성에 더한 뒤 이동 상태를 별도 저장한다. `sendFleet` 소켓은 연결 이벤트로 등록되지 않는다.
- 공격 API는 함선 종류를 `slice(0, 8)`로 잘라 전투 덱을 만든다. 편성 전체가 전투에 참여하도록 이 경계를 검증해야 한다.
- `docker-compose.yml`의 MongoDB는 replica set 설정이 없는 단일 인스턴스다. 현재 설정에서 다중 문서 트랜잭션을 사용할 수 있다고 가정하면 안 된다.
- `tasks/fleet-strike-map.md`는 이전 지도 작업의 완료 기록이다. 변경하지 않고 이번 후속 작업을 이 파일에 기록한다.
- 저장소에 많은 기존 미커밋 변경이 있다. 구현 시작 시 Git 상태를 재확인하고 관련 현재 코드를 기준으로 패치한다.

## 화면과 동작 설계

### 사용하기 쉬운 시각적 구성

- 정보 우선순위는 `내 함대가 어떻게 구성됐는가 / 지금 무엇을 할 수 있는가 / 어디로 보내는가 / 언제 돌아오는가`다. 긴 설명·좌표 입력·세부 숫자를 첫 화면에 모두 펼치지 않는다.
- 기존 남색·황동색 사령부 분위기는 유지하되 넓은 이미지 영역, 카드 간 여백, 짧은 제목, 뚜렷한 선택 상태와 주요 행동 버튼으로 읽기 부담을 줄인다. 작은 한자 부제·장식 선·세부 표가 핵심 조작과 경쟁하지 않게 정리한다.
- 함선 식별은 기존 카탈로그의 3D 모델 썸네일을 활용한다. 함종 이름과 수량도 함께 표시해 이미지나 색만으로 판단하게 하지 않는다. 이미지가 늦게 로드돼도 카드 크기와 버튼 위치는 유지한다.
- 함대 화면은 `함대 카드 목록 / 선택한 함대의 시각적 편성 영역 / 배정 가능한 함선 카드`로 구성한다. 편성 영역은 함선 이미지와 `경전투기 × 20`처럼 조합을 보여준다. 화면상의 카드 위치는 전투 진형/웨이브 효과를 의미하지 않는다.
- 함선 카드를 선택하면 편성에 추가되고 카드 안에서 +/−, 수량 입력, `가능 수량 모두 배정`으로 조절한다. 빠른 추가·제거와 배정 가능 수량을 바로 보여준다. 드래그 배정은 보조 동작으로 제공할 수 있으나 클릭·터치로도 모든 편성 작업을 완료할 수 있어야 한다.
- 함대 카드에는 대표 함선 이미지 묶음, 이름, 총 척수, `대기 / 출격 중 / 귀환 중 / 빈 편성` 상태를 표시한다. 세부 공격력·적재량·속도는 선택한 함대의 요약/상세에서 보여준다.
- 저장 버튼과 변경 여부는 눈에 잘 보이는 편집 영역 하단에 둔다. 미저장 초안으로 다른 함대/메뉴를 선택하면 저장·버리기·계속 편집 선택을 제공해 수정 유실을 막는다. 해산은 별도 메뉴로 분리하고 대상 함대를 명시해 확인한다.
- 전투 화면은 지도를 주 영역으로, `출격 가능한 함대`를 옆 카드 목록으로, `진행 중인 임무`를 아래 영역으로 구분한다. 좌표 수동 입력과 전투 보고는 접을 수 있는 보조 영역에 둔다.
- 함대 선택·드래그 시작·유효 목표·출격 확인·처리 중·성공/실패를 화면 가까이에서 보여준다. 선택된 카드와 목표를 함께 강조하고 화살표에 ETA를 표시한다. 성공 시 카드 제거와 임무 카드 등장에 짧은 전환 효과를 주며 모션 감소 설정을 존중한다.
- 진행 중인 임무는 긴 텍스트 한 줄 대신 함대 이미지·이름, 목적지, `진군 중 / 귀환 중`, 카운트다운과 해당 구간 진행 막대를 갖는 카드로 표시한다. 시간은 서버 시간 기준으로 계산한다.
- 비활성 버튼 가까이에 이유를 표시한다. 빈 함대에는 `함선 배정`, 함대가 없는 전투 화면에는 `함대 만들기`처럼 다음 행동을 바로 제공한다. 오류는 해당 수량/목표/카드에 표시하고 전체 화면을 초기화하지 않는다.
- 모바일은 함대 선택 → 편성/지도 → 임무 순서로 쌓는다. 주요 조작은 최소 44px 터치 영역을 확보하고 가로 스크롤 없이 사용하게 한다. 키보드 포커스·선택 상태·색 대비와 클릭 출격 경로를 함께 확인한다.

### 함대

- 왼쪽: `함대 생성`과 1함대·2함대 등의 목록. 오른쪽: 선택한 함대 이름, 출발 행성, 종류별 함선 수량, 척수·공격력·적재량·속도 요약, 저장·해산.
- 기본 이름은 사용자 단위의 증가 번호로 부여한다. 삭제한 번호는 자동 재사용하지 않는다. 이름 변경은 허용하고 식별에는 고정 ID를 사용한다.
- 생성은 현재 행성에 빈 함대를 만든다. 빈 함대는 저장할 수 있으나 출격할 수 없다.
- 편성은 우선 함선 종류·수량 조합으로 제공한다. 새 진형/웨이브 조작 규칙은 추가하지 않는다. 전투 덱 변환은 서버에서 처리한다.
- 보유량 / 다른 함대에 배정된 수량 / 배정 가능한 수량을 구분한다. 편집 시 자기 함대의 기존 배정량은 사용 가능 수량에 포함한다.
- 함선 배정은 주둔 수량 안에서 예약한다. 편성 저장 자체가 행성의 주둔 함선을 차감하지 않는다. 해산은 예약만 해제한다.
- 출격·귀환 중인 함대는 목록에 상태와 임무 바로가기를 표시하며 편집·해산·재출격을 막는다.
- 저장 전 수정은 초안이다. 취소하면 서버 편성을 유지한다. 서버 수량/버전과 충돌하면 새 상태를 보여주고 초과 배정을 설명한다.

### 전투

- 상단/중앙: 기존 궤도 지도와 성계 이동. 옆에는 현재 행성에 속한 대기·비어 있지 않은 함대의 개별 드래그 카드가 나열된다.
- 카드: 함대 이름, 주요 함선 구성, 총 척수·공격력. 함대가 없으면 함대 화면으로 연결한다. 함선 수량 편집은 함대 화면에서 한다.
- 카드를 놓으면 기존 확인 흐름을 유지한다. 카드 ID·편성 버전·목표를 고정하고 해당 함대의 속도로 ETA를 계산한다.
- 빈 궤도·출발 행성은 무효. 기존 아군 수송 경로도 저장된 함대 선택으로 유지한다. 적 행성 기본 임무는 공격이다.
- 확인 취소나 출격 실패 시 카드는 유지한다. 요청 중에는 해당 카드와 확인 버튼을 잠근다.
- 서버 성공 응답의 최신 스냅샷으로 카드 목록과 하단 `진행 중인 임무`를 함께 갱신한다. 단순 드롭만으로 카드를 제거하지 않는다.
- 임무에는 함대 이름·임무 종류·목표·출발지·남은 시간·현재 척수와 진군/귀환 상태를 보여준다. 귀환 중에도 카드로 돌아오지 않는다.
- 새로고침·재접속 시 서버 상태로 같은 배치를 복원한다. 클릭/키보드 목표 선택·출격 경로, 모바일 Pointer Events·자동 스크롤도 유지한다.
- 기존 좌표 입력 폼을 유지할 경우 함선 직접 선택을 제거하고 저장된 대기 함대를 선택하도록 바꾼다. 성계도 `작전 목표 지정`은 전투 화면으로 연결한다.

## 데이터·API 설계안

- 사용자 내 `fleetFormations[]`를 추가한다: `id`, `number`, `name`, `originPlanetId`, `ships`, `status(ready/onMission)`, `activeMovementId`, `revision`. 빈 편성 여부는 수량으로 계산한다.
- 행성 인덱스 대신 행성의 고정 `_id`로 소속을 연결한다. 생성·출격은 현재 행성에서 하고, 저장된 편성의 수정·해산은 소유한 해당 행성의 수량으로 검증한다. 전역 목록에는 소속 행성과 상태를 구분해 표시한다.
- `planets[].fleet`는 계속 주둔 함선 총량이다. 타입별 미배정량 = 주둔량 − 대기 함대 예약량. 임무 중 편성은 주둔 예약량에서 제외한다.
- 이동 문서에 `formationId`, `formationNameAtLaunch`, `formationRevisionAtLaunch`, 출발 시 함선 구성을 보존한다. `fleet`는 현재 생존 함선이다. 임무 이름은 출격 당시 이름으로 표시한다.
- `FleetMovement.fleet`는 카탈로그의 함선 ID를 수용하도록 바꾸고, 카탈로그·속도·양의 정수 검증은 서버에서 한다. 기존 이동 문서는 그대로 읽을 수 있어야 한다.
- 제안 API: `GET/POST /api/game/fleet-formations`, `PATCH/DELETE /api/game/fleet-formations/:id`. 생성·수정·해산은 최신 스냅샷을 반환한다.
- 기존 `POST /api/game/fleets`는 `formationId`, `expectedRevision`, `requestId`, `mission`, `destination`, `cargo`, `speed`를 받는다. 함선 구성·출발지는 서버가 편성에서 읽는다. 클라이언트의 수량 위조나 다른 행성/사용자 편성은 거부한다.
- 기존 raw `fleet` 출격은 새 클라이언트에서 사용하지 않는다. 구 클라이언트 요청은 명시적인 편성 필요 오류로 거부한다. 예약된 함선을 우회 소비하는 경로를 남기지 않는다.
- 스냅샷에 편성·미배정량·연결된 임무를 포함하고 `GameState`는 합쳐서 남은 옛 데이터를 유지하지 않고 최신 목록으로 교체한다.
- 기존 사용자는 빈 편성 목록과 기존 함선 수량으로 시작한다. 편성 ID가 없는 기존 임무는 `기존 임무`로 계속 처리하며 함대를 자동 생성하지 않는다.

## 재검토로 보완한 경계

- **결과를 알 수 없는 출격:** 서버가 성공했어도 응답이 유실될 수 있다. 타임아웃은 확정 실패로 처리하지 않고 `결과 확인 중`으로 해당 함대를 잠근다. 동일 requestId로 재조회/재요청해 결과를 확정하며 새 ID를 만들지 않는다. 출격 성공 후 snapshot 생성만 실패한 경우도 같은 경로로 복구한다. 요청 ID는 사용자별 고유 인덱스로 보장하고 동일 ID에 다른 요청 내용을 보내면 충돌을 반환한다.
- **실시간 갱신:** 출격·전투·귀환·편성 수정 커밋 후 사용자 단위로 상태 변경 알림을 보내고 모든 인증된 연결이 최신 스냅샷을 받거나 조회하도록 한다. 연결 복구·창 재활성화 시 재조회한다. 임무가 있는 동안 소켓이 끊기면 제한된 주기로 재조회하고, 화면 이탈 시 타이머를 정리한다. 카운트다운 0은 서버의 상태 전이를 의미하지 않으며 `도착 처리 중`으로 표시한다.
- **오래된 응답과 편집 초안:** 상태 변경에 사용자 단위 증가 버전을 포함하고 구버전 응답이 최신 출격 상태를 덮어쓰지 못하게 한다. 자동 갱신은 편집 초안을 초기화하지 않는다. 서버 편성이 변경되면 충돌을 표시하고 최신 상태 기준 재검증/재편집 경로를 제공한다. 행성 전환·로그아웃·목표 변경 시 진행 중 드래그/확인 카드를 정리한다.
- **방어전과 편성:** 예약은 함선을 방어전에서 제외하지 않는다. 주둔 중인 배정/미배정 함선 모두 기존 방어 규칙의 대상이다. 실제 발생한 손실에 따라 편성을 조정한다. 공격 중 함선은 주둔량에서 빠지므로 방어에 참여하지 않는다. 임무 중 편성의 현재 척수는 이동 문서의 생존 수량을 기준으로 표시한다.
- **입력·목표 검증:** 함대 전체 출격만 허용한다. 일부만 보내려면 함대 화면에서 먼저 분리한다. 서버는 소유자·출발 행성 ID·편성 버전·허용 임무·속도·적재량·목표 행성 ID를 다시 검증한다. 목표 행성이 드래그 이후 변경되면 재확인을 요구한다. 자기 행성 공격은 차단하고 자기 다른 행성 수송은 허용한다. 이름은 공백 제거 후 1~40자, 번호는 원자적 증가로 발급하며 같은 사용자 내 이름 중복은 거부한다.
- **전투 덱 호환:** 자동 배치 순서는 클라이언트 선택 순서 대신 서버 카탈로그의 고정 순서를 사용한다. 8웨이브 자체는 유지하면서 한 웨이브가 여러 함종을 수용하도록 입력 어댑터를 확장한다. 기존 단일 함종 슬롯도 읽는다. 전체 웨이브의 입력 합계가 출격 수량과 일치해야 한다. 기존 임무의 실제 저장 함선이 덱에서 누락된 경우도 복구·검증 대상이다. 방어측의 첫 함종만 반영되는 기존 경계도 확인하고 주둔 함종 전체가 손실 정합화 대상이 되도록 한다.
- **원자성의 적용 범위:** 현재 `settleUserState`도 행성 문서를 저장한다. 출격·방어 피해·귀환뿐 아니라 정산·건조 완료·관리자 변경 등 같은 수량을 쓰는 경로가 공통 버전/조건부 갱신 또는 트랜잭션을 사용해야 한다. 타이머 재진입·서버 다중 실행·재시작에서도 임무 처리의 조건부 상태 전환을 보장한다. 알림은 DB 커밋 이후에만 전송한다.
- **DB 방식 확정:** 새 함대 변경에는 MongoDB replica set과 다중 문서 트랜잭션을 필수 조건으로 채택한다. 기존 standalone 서버 시작·로그인·정산·건조·관리 경로는 유지한다. 출격·전투·귀환과 관련 수량 갱신은 같은 계약을 사용한다. standalone 단일 문서 대안은 이번 구현 범위에서 제외한다. 환경 구성 확인/격리 테스트 replica set 준비는 P1-S1의 구현 작업이며 사용자에게 별도 설계 결정을 요구하지 않는다. 실제 DB 구성 전환은 백업·기존 볼륨 보존·연결/복구 검사 후 진행하고, 환경 조건을 충족하지 못하면 배포 완료로 표시하지 않는다.
- **범위 확정:** 출격 후 수동 취소/회군과 다른 행성으로 함대 소속 이동은 첫 버전에 제공하지 않는다. 기존 cancelled 임무가 있으면 완료된 기존 기록으로 보존한다. 원래 행성이 사라진 임무는 함선을 임의 삭제하지 않고 오류·복구 대상으로 남긴다. 첫 버전의 함대 개수에는 게임 규칙상 새 상한을 추가하지 않되 긴 목록의 스크롤/렌더링을 검증한다.

## 상태·함선 보존 규칙

1. 생성/수정/해산은 대기 함대에만 허용한다. 속도 0 함선은 편성 대상에서 제외한다.
2. 같은 행성의 모든 대기 함대 배정 합계가 주둔 수량을 넘지 않게 서버에서 검증한다. 동시 편성 저장도 동일 조건을 보장한다.
3. 출격은 `대기 확인 + 버전 확인 + 함선/적재 자원 차감 + 이동 생성 + 함대 임무 연결`을 하나의 원자적 처리로 완료한다.
4. 동일 `requestId` 재요청은 같은 출격 결과를 반환한다. 서로 다른 ID로 같은 함대를 동시에 보내도 하나만 성공한다.
5. 전투 후 임무의 생존 함선을 기록한다. 귀환 완료 시 생존 수량만 주둔량에 더하고 같은 함대에 예약해 대기로 바꾼다. 잃은 함선은 자동 충원하지 않는다.
6. 전멸은 함대 이름/ID를 보존하고 빈 편성으로 만든다. 드래그 목록에는 나타나지 않으며 함대 화면에서 다시 편성한다.
7. 귀환 처리 재실행은 함선을 두 번 더하지 않는다. 도착 전투 처리 역시 중복 실행으로 피해/전리품을 반복 적용하지 않는다.
8. 대기 함선이 방어전 손실 등으로 감소하면 예약도 정합화한다. 단순 규칙: 함대 번호 순서로 남은 함선을 배정하고 부족한 뒤쪽 편성 수량을 줄이며 변경을 표시한다. 관리자 수량 변경도 같은 정합화 경계를 거친다.

## 변경 경계와 구현 단계

각 단계는 아래 step ID 순서로 구현·검증했다. 단계별 세부 체크리스트와 검증 근거를 함께 기록한다.

### 확정한 구현 계약

- DB: replica set + 트랜잭션. 편성 변경은 같은 사용자 문서에 대한 조건부 버전 갱신으로 직렬화한다. 출격·전투·귀환은 사용자/이동/보고서를 트랜잭션 안에서 함께 반영한다. 모든 참여 수량 갱신 경로도 같은 서비스 경계를 사용한다.
- 버전: `User.stateRevision`을 상태 변경 시 원자적으로 증가시킨다. 모든 스냅샷은 이 값을 포함한다. 같은 버전의 시간/자원 갱신은 `serverTime`으로 정렬하고 클라이언트는 이전 버전 또는 이전 시각 응답을 적용하지 않는다. 편성 변경에는 별도 `formation.revision`을 사용한다.
- 요청: `FleetMovement`의 `{userId, requestId}`에 부분 고유 인덱스를 둬 requestId가 없는 기존 임무도 보존한다. 요청 내용 해시를 기록한다. 동일 요청 재시도는 기존 이동 ID와 결과를 반환하고 내용이 다르면 409다. `GET /api/game/fleet-requests/:requestId`로 상태를 조회한다. 404와 통신 실패를 구분하고, 미확정 요청은 같은 ID 재요청으로만 복구한다.
- 출격 입력: 기존 설계 필드에 `originPlanetId`, `expectedTargetPlanetId`를 포함한다. 현재 선택 행성이 바뀌었거나 목표 행성의 정체가 바뀌면 409로 재확인을 요구한다. 소유권·편성·주둔량은 트랜잭션 내부의 최신 문서로 검증한다.
- 응답: CRUD 성공은 `formationId/stateRevision/snapshot`, 출격 성공은 `fleet/stateRevision/snapshot`을 반환한다. 커밋 후 스냅샷 읽기 실패는 성공한 `fleet`와 `snapshotPending: true`를 반환해 재동기화한다. 400은 잘못된 입력, 401은 인증 실패, 404는 접근 가능한 대상 없음, 409는 버전/상태/수량/요청 내용 충돌, 503은 일시적 처리 불가다. 클라이언트 안내는 오류 code별로 제공한다.
- 전투 입력: `deckVersion: 2`, 길이 8의 `combatWaves`, 각 웨이브 `{ships: {shipId: count}, defense: {defenseId: count}}`를 사용한다. 공격 함종을 서버 카탈로그 고정 순서로 정렬하고 i번째 종류를 `i % 8` 웨이브에 넣는다. 종류별 수량은 나누지 않으며 9번째 이후도 누락하지 않는다. 방어시설 전체는 0번, 주둔 함선 전체는 1번 웨이브에 배치한다. 기존 `fleetDeck`은 어댑터로 변환하고 실제 함선 수량과 누락 차이가 있으면 남은 종류를 동일 순서로 보충한다. 발사·피해·승패 공식은 유지하고 웨이브별 초기 투입만 다중 함종으로 확장한다.
- 도착 처리: 이동의 조건부 상태 전환과 피해·전리품·보고서 생성을 한 트랜잭션에서 반영한다. 보고서의 이동 ID도 고유하게 둔다. 재시도 가능한 전투 계산은 이동별 고정 난수 seed를 사용하거나 계산 결과를 고정해 중복 재시도 결과가 달라지지 않게 한다.
- 대상 소실: 출발 뒤 목표 행성이 사라지면 전투/수송을 실행하지 않고 함선과 적재 자원을 보존해 귀환 처리하며 사유를 기록한다. 출발 행성이 사라지면 수량을 버리지 않고 복구 필요 상태로 남긴다.

## 구현 중 확정한 사항

- DB 환경은 기존 27017/3000/5173을 사용하지 않고 전용 MongoDB 27029 / 서버 3999 / Vite 5179로 분리했다. 기본 서버는 standalone에서도 기존 기능을 유지하고 새 함대 변경만 거부한다. 2026-10-05 기존 DB를 replica set으로 전환해 이 제한을 해결했다.
- 생성·출격은 현재 행성 기준이다. 다른 소유 행성의 저장된 함대도 소속 행성의 재고로 수정/해산할 수 있도록 했다. 행성 간 함선 이동은 추가하지 않았다.
- 화면 비활성 상태의 공통 타이머는 네트워크/렌더 작업을 건너뛴다. 드래그 종료 시 자동 스크롤 프레임과 화살표를 정리한다. 스냅샷이 같으면 임무 카드를 재생성하지 않는다.
- 편성 생성 시 사용자가 미리 이름 붙인 `N함대`와 기본 이름이 겹치면 번호를 다음으로 넘긴다. 번호/이름을 자동 재사용하거나 기존 함대를 바꾸지 않는다.
- 실행/검증/정리 안내는 `docs/fleet-development.md`, 기존 볼륨을 보존하는 DB 구성은 `docker-compose.fleets.yml`에 기록했다.

- 실제 실행 환경 적용은 replica set 연결 준비와 백업/복구 확인 후 수행한다. 현재 결과를 배포 완료라고 표시하지 않는다.
- 사용자가 구현과 UI를 확인한 뒤 조작/시각 개선 피드백을 반영한다. 하네스 스킬 반영 여부는 그 후 판단하며 스킬 파일은 변경하지 않았다.

## 기존 환경 회귀 수정 (2026-10-04)

- 새 replica set 시작 조건이 기존 standalone 서버 전체를 종료시키는 회귀를 확인하고 제거했다. 공통 정산·건조·관리 경로는 기존 standalone 실행을 지원하고, 새 함대 변경은 mutation 전에 503으로 차단한다. 기존 편성 없는 임무 귀환은 계속 처리한다.
- 실제 기존 DB 사용자 2명 존재 확인. 실제 서버 3000의 사용자 스냅샷·카탈로그·건조 대기열·성계 API가 모두 200 응답. 기존 프런트 5174에서 로그인 화면 및 Server Online 표시 확인. 실제 비밀번호 로그인과 로그인 이후 화면 조작은 미확인.
- 별도 standalone DB에 HTTP 로그인·사용자 스냅샷·건조 요청·새 함대 차단(무차감)·기존 귀환 회귀 검사 추가. standalone와 replica set 통합 테스트 포함 61개 통과.
- 사용자에게 다른 구체적인 고장 증상을 요청한 상태. UI 전체 복구나 새 함대의 실제 환경 동작이 완료됐다고 판단하지 않는다.

## 실제 DB 함대 연결 복구 (2026-10-05)

- 사용자에게 표시된 트랜잭션 필요 오류의 원인은 실제 MongoDB의 standalone 실행 설정이었다. Colima 포트 포워딩 뒤 `ogame-mongo`를 확인했으며 외부 DB가 아니었다.
- 실제 서버를 잠시 중단하고 6개 컬렉션 134개 문서를 압축 백업했다. 별도 DB에 복원해 컬렉션별 문서 수·해시가 원본과 일치함을 검증했다.
- 기본 Compose의 MongoDB에 replica set 설정을 추가했다. 기존 Compose 프로젝트 `gorgonian` 및 동일 `gorgonian_mongo_data` 볼륨·MongoDB 이미지 버전을 유지해 재시작하고 `oogame` 단일 노드 replica set을 초기화했다. 전환 직후 원본 문서 해시가 전부 일치했다.
- 로컬 서버 `.env`에 replicaSet 및 directConnection 옵션을 적용하고 기존 nodemon 서버를 재시작했다. 실제 DB에서 트랜잭션 완료 확인. 실제 서버 HTTP 로그인 200·함대 생성 201·5척 편성 저장 200·재조회 200 확인. 검사에 사용한 임시 계정만 삭제했고 기존 사용자 2명이 유지된다.
- 기본 Compose와 `.env.example`에 실행 조건을 반영했다. 백업은 `artifacts/db-backups/`에 비공개 권한으로 보관하고 Git에서 제외한다. 화면 로그인 이후 조작은 이번 복구에서 별도로 수행하지 않았다.
