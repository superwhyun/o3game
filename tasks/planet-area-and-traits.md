# 행성 면적·특성·테라포밍 계획

작성일: 2026-10-05
상태: in_progress — 구현·로컬 검증 완료, 최종 커밋·main 머지 대기. 배포·push는 요청되지 않음.
진행 방식: harness. 이 문서를 단일 작업 기록으로 사용한다.

## 목표와 사용자 경로

플레이어가 소유 행성을 선택하면 해당 행성의 크기, 개발 가능 비율, 건물 사용 면적, 예약 면적, 남은 면적과 생산 특성을 확인한다. 신규 건설 및 업그레이드는 면적을 소비한다. 후반 테라포밍 연구는 행성의 크기를 바꾸지 않고 개발 가능한 비율을 늘린다. 행성별 광물 특성과 온도는 실제 서버 생산량에 반영된다.

행성 전체 면적은 절대 한도이며, 가용률은 100%를 넘지 않는다. 함대와 연구는 지상 건설 면적을 소비하지 않는다. 함대 배치·식민지 개척 시스템 완성은 이번 범위에서 제외한다. 기존에 여러 행성을 가진 계정의 선택·건설 경로는 이번 범위에 포함한다.

## 확인한 현재 구조

- `server/models/User.js`: planets 배열 안에 건물·함대·연구·지름·온도가 저장되어 있다. 면적·가용률·매장 특성은 없다.
- `server/routes/buildingQueue.js`: 건설 요청의 planetId 기본값은 0이며 잘못된 대상도 첫 행성으로 대체한다. 선행 조건·자원은 검사하지만 면적은 검사하지 않는다. 건설 큐 조회는 사용자 기준이다.
- `server/socket/handlers.js`: 별도의 즉시 건설·연구 경로가 있어 HTTP 큐만 수정하면 규칙을 우회할 수 있다.
- `server/services/GameStateService.js`: 큐 완료와 오프라인 생산, 스냅샷의 중심 경로다. 연구 스냅샷은 선택한 행성의 연구를 읽는다.
- `server/utils/planetEconomy.js`: 서버 생산 계산에 온도가 반영되지 않는다. 클라이언트 데이터의 온도 공식과 실제 서버 결과가 다를 수 있다.
- `ogame-3d/src/ui/UIManager.js`, `services/ApiService.js`: 건설 UI가 명시적인 행성 대상을 전달하도록 정리해야 한다.
- `server/package.json`: test 스크립트는 jest지만 선언된 의존성에 jest가 없다. 검증 도구가 준비되었다고 가정하지 않는다. 클라이언트에는 Vite build가 있다.
- 계획 작성 전 Git 작업 트리는 깨끗했고, 기존 관련 task 문서는 발견하지 못했다.

## 설계안

### 면적과 건물

게임 면적 단위는 칸으로 표시한다. 실제 구 표면적에 비례하도록 지름 제곱으로 환산한다.

```text
totalArea = floor((diameterKm / areaScaleKm)^2)
usablePercent = min(100, baseUsablePercent + terraformLevel * percentPerLevel)
usableArea = floor(totalArea * usablePercent / 100)
usedArea = 모든 건물 레벨의 합계
availableArea = max(0, usableArea - usedArea - reservedArea)
```

- 초기 후보값: areaScaleKm=1000, 기본 가용률 40%, 테라포밍 레벨당 +2%p.
- 예: 지름 12,800km → 전체 163칸 → 기본 65칸. 테라포밍 5레벨이면 가용률 50%, 81칸. 반올림 규칙은 전체·가용 면적 모두 내림으로 통일한다.
- 위 수치는 확정 밸런스가 아니다. 현재 건물 레벨 성장과 필요한 연구소·광산·조선소 공간을 계산해 초중반 진행을 막지 않는 값으로 조정한다.
- 모든 건물은 레벨 1당 1칸. 종류별 별도 건물 수 제한 대신 면적 제한으로 처리한다. 동일 종류 건물 여러 채 건설은 추가하지 않는다.
- 다음 레벨은 완료 레벨과 유효 예약 레벨을 함께 고려한다. 같은 건물을 연속 예약해도 레벨·공간을 중복 또는 누락 계산하지 않는다.
- 면적은 건설 예약 시 확보한다. 완료 시 예약분을 사용분으로 전환하며, 취소하면 예약분을 반환한다. 완료·취소 재처리로 이중 차감·반환하지 않는다.
- HTTP와 Socket 경로는 같은 서버 규칙을 사용한다. 동시 요청의 자원 차감·공간 확보·큐 생성은 하나의 일관된 쓰기 절차로 처리한다. MongoDB 트랜잭션 지원 환경을 확인하고, 미지원이면 사용자 단위 직렬화와 실패 복구 절차를 설계·검증한다. 여러 서버 인스턴스에서 프로세스 내부 잠금만으로 안전하다고 간주하지 않는다.

### 테라포밍과 연구 범위

- 후반 연구 `terraforming`을 추가한다. 플레이어 공통 레벨로 소유 행성 전체에 적용한다. 큰 행성은 동일한 %p 상승으로 더 많은 면적을 확보한다.
- 기존 일반 연구 전체를 전역화하는 작업은 포함하지 않는다. 테라포밍의 공통 저장 위치와 조회 규칙을 명시하고, 기존 행성별 연구와 충돌 없이 스냅샷에 병합한다. 새 필드가 기존 `user.research` fallback의 의미를 바꾸지 않도록 한다.
- 초기 선행 조건 후보: 연구소 10, 에너지 기술 12, 천체물리학 4. 비용·시간 증가율과 최대 레벨은 성장 분석 후 같은 문서에 확정한다.
- 기본 가용률이 최소 40%인 초기안에서는 30레벨로 100%에 도달한다. 가용률 분포를 바꾸면 최대 레벨도 함께 재검토한다. 효과 없는 추가 연구는 막는다.
- 연구 수행 행성을 명시하며, 선행 건물·자원은 그 행성에서 검사·차감한다. 연구 자체는 면적을 소비하지 않는다.
- 연구 완료 시 모든 행성의 가용 면적을 재계산한다. 진행 중인 연구의 효과는 미리 적용하지 않는다.

### 행성 특성과 생산

- 영구 특성: 금속·크리스털 매장 보정, 온도, 환경에 따른 기본 가용률. 행성 생성 시 저장하고 조회·접속 때 재추첨하지 않는다.
- 매장 보정 후보 범위: 0.8~1.2. 금속·크리스털의 광산 생산에 각각 적용한다. 기본 무료 생산은 보정하지 않는다.
- 온도가 낮을수록 중수소 생산, 높을수록 태양광 발전에 유리하게 한다. 온도 입력은 min/max 평균으로 통일하고 효과는 후보 범위 0.8~1.2 안으로 제한한다. 정확한 기준 온도·기울기는 성장 분석에서 확정한다.
- 기후는 기본 가용률에 반영한다. 기후·온도 생산 보정을 별도로 중첩하지 않아 규칙을 단순하게 유지한다. 특정 기후를 무조건 우월하게 만들지 않는다.
- 순서: 기존 건물 생산 공식 → 해당 행성 보정 → 서버 생산 배율·속도. 에너지 소비 공식은 기존 규칙을 유지한다.
- 온라인 표시·오프라인 누적·건설 완료 전후 생산·관리자 미리보기에서 같은 계산을 사용한다. 변경 시점 이전 생산은 이전 상태로 정산하고 이후부터 새 효과를 적용한다.

### 철거 및 기존 데이터

- 건물 레벨을 1씩 낮추면 1칸을 회수한다. 기본 자원 환급은 없다. 소요 시간은 건설 시간 체계에 맞춰 결정한다.
- 선행 조건이 필요한 건물·연구의 진행 중 작업이 있으면 관련 시설 철거를 막는다. 철거 후 기존 상위 시설은 유지하되, 신규 작업의 선행 조건은 현재 레벨로 검사한다.
- 동일 건물의 업그레이드·철거 동시 진행은 막는다. 저장고 철거로 저장 한도가 줄면 손실 가능량을 사전에 보여주고 기존 자원 상한 정책을 일관되게 적용한다.
- 기존 행성에는 중립 매장 보정 1.0을 부여하고 기존 지름·온도를 보존한다. 누락값만 기본값으로 보정하며 숫자 0을 누락으로 처리하지 않는다.
- 사전 dry-run에서 완료·예약 건물 면적을 집계한다. 전체 면적 한도 내에서는 기존 진행을 수용하도록 기본 가용률을 보정하고 원래 계획값과 보정 내역을 기록한다.
- 기존 사용+예약 면적이 전체 면적보다 큰 경우 자동으로 행성 크기를 바꾸거나 건물을 삭제하지 않는다. 예외 계정을 보고하고, 기존 작업은 보존하되 신규 건설을 차단하는 전환 정책을 확정한 후 적용한다.
- 마이그레이션은 재실행 가능하게 하고 적용 전 백업·dry-run 결과를 남긴다. 실제 데이터 변경은 구현 요청 이후 해당 환경에 대한 권한 범위 안에서 수행한다.

## 공개 계약 및 실패 처리

- 스냅샷의 각 행성에 `area: { total, baseUsablePercent, usablePercent, usable, used, reserved, available }`, `traits`, `productionModifiers`를 추가한다. 기존 생산·자원 필드는 유지한다.
- 스냅샷에 테라포밍 공통 레벨과 행성 선택 대상을 제공한다. 사용·가용 면적은 서버 계산 결과가 기준이다.
- 건설·철거·행성 기반 연구 요청은 유효한 소유 행성을 명시한다. 기존 배열 인덱스를 당장 사용할 경우 선택·큐·취소까지 동일하게 유지하고, 잘못된 인덱스를 첫 행성으로 대체하지 않는다.
- 오류 코드 후보: `INVALID_PLANET`, `INSUFFICIENT_AREA`, `INSUFFICIENT_RESOURCES`, `REQUIREMENTS_NOT_MET`, `BUILDING_BUSY`, `TERRAFORMING_MAX_LEVEL`. 면적 부족 응답에는 필요한 면적과 남은 면적을 포함한다.
- 실패 시 자원만 차감되거나 큐만 남거나 공간만 예약된 상태를 만들지 않는다. 취소 시 기존 자원 환급 정책은 유지한다.

- 범위: 명시적인 대상 선택, 건설·연속 업그레이드·완료·취소의 공간 수명 주기, HTTP/Socket 공통 검증, 동시 요청 일관성. 예상 경계: buildingQueue, BuildingQueue 모델, GameStateService, socket handlers, ApiService.

- 완료 조건: 남은 1칸에 동시 요청 2개 중 하나만 수락된다. 같은 건물 연속 예약 레벨이 올바르고, 취소·중복 완료 후 사용 면적이 정확하다. 다른 행성의 자원·건물·면적에 영향이 없다.
- 검증: DB 통합 테스트로 예약·취소·완료·실패 복구·동시 요청 검증. HTTP와 Socket 모두 같은 제한 확인. 큐 완료 후 재접속 스냅샷 확인.

### U4 — 특성 생산 및 테라포밍 성장

- 상태: completed. 선행: U1, U2.
- 범위: 새 행성 생성의 특성 부여, 서버 생산 보정, 공통 테라포밍 연구·선행 조건·비용·완료 효과. 예상 경계: entity defaults/catalog, User, planetEconomy, buildingQueue, GameStateService.

## 구현 중 설계 갱신 (2026-10-05)

- main의 새 함대·카탈로그·트랜잭션 커밋(5387ace)을 현재 브랜치로 먼저 반영했다. 기존 코드 관찰보다 최신 구조를 기준으로 구현한다.
- 시작 지름 12,800km에서 256칸/기본 102칸이 되도록 areaScaleKm=800을 채택한다. 광산 15+12+10, 발전소 15, 연구소 10, 로봇 8, 조선소 5, 저장 시설 합계 12 = 87칸으로 테라포밍 선행 시설까지 도달 가능하다. 초기 가용률은 40~50%다.
- 테라포밍: 연구소10/에너지12/천체물리4, 기본 비용 금속100000/크리스털150000/중수소100000, 비용·시간 배율1.6, 기본7200초, 최대30레벨. 플레이어 공통 terraformingLevel 필드를 사용한다.
- 기본 무료 생산에는 매장 보정을 적용하지 않는다. 평균10°C를 중립으로 온도 1°C당 0.2% 효과, 보정0.8~1.2. 지름·온도0을 보존한다.
- 원자적인 큐·자원·예약 처리를 위해 건설/연구/철거/유닛생산/취소는 기존 함대 기능과 같은 replica set DB가 필요하다. standalone에서는 변경 요청을503으로 거부하고 읽기·로그인은 유지한다. 기존 compose의 docker-compose.fleets.yml을 재사용한다. 이 호환성 변경을 standalone 회귀 테스트와 운영 안내에 명시한다.
- 커밋은 사용자 요청대로 모든 구현·검증을 마친 마지막에 묶어서 수행한다. main의 별도 미커밋 변경을 보존한다.
